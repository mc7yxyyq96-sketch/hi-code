# Credential Storage

Status: Implemented in HC-SEC-401

Hi Code separates credential values from persisted configuration. Model, MCP,
and Agent Provider configuration files contain opaque references; the desktop
main process stores encrypted values through Electron `safeStorage`.

## Desktop Storage Model

The desktop uses these app-data files:

- `config.json`: non-secret model and MCP configuration plus `secretRef` values
- `providers/providers.json`: non-secret Agent Provider state plus provider
  `secretRef` records
- `secrets/vault.json`: versioned encrypted values and encrypted migration
  snapshots
- `secrets/migration-journal.json`: hashes, reference IDs, timestamps, and
  migration state; never credential values

References are validated, versioned, and scoped:

```text
hicode-secret:v1:model:<profile>
hicode-secret:v1:mcp:<server>:<environment-field>
hicode-secret:v1:provider:<provider>:<field>
```

Segments are encoded and bounded. References are generated by Hi Code and are
not credentials. Manually copying a reference does not copy its encrypted value.

The renderer can read only sanitized config and a status projection containing
reference IDs plus `configured: true|false`. It cannot read, decrypt, or request
credential values. Saved keys are never repopulated into password inputs.

## Platform Backends

Electron selects the operating-system backend:

- macOS: Keychain
- Windows: DPAPI
- Linux: a supported secret service backend selected by Electron

Hi Code rejects an unavailable backend and rejects Electron's Linux
`basic_text` backend. In that state desktop credential writes fail closed and
the existing config bytes remain unchanged. The UI reports that secure storage
must be restored or the credential must be supplied through the CLI environment.

## Save And Rotation Transaction

Saving model or MCP settings performs one guarded transaction:

1. Parse and validate the config object.
2. Replace plaintext model keys and sensitive MCP environment values with
   scoped references.
3. Encrypt new values with `safeStorage` and atomically replace the private
   vault file.
4. Atomically replace `config.json` with the sanitized form.
5. Restore both previous files if either write fails.

Provider configuration uses the same encrypted vault. Secret fields declared
by a Provider schema, and secret-like field names, are externalized before
`providers.json` is written. Blank or omitted secret inputs preserve an existing
reference; rotation replaces only the encrypted value.

Files and parent directories use owner-only permissions where the platform
supports POSIX modes. Logs contain event names, counts, reference IDs, and error
codes only. They never contain plaintext or ciphertext.

## Legacy Migration And Recovery

After `app.whenReady()`, before services or Runtime start, the desktop scans the
legacy config for plaintext model and sensitive MCP credentials. A successful
migration:

- encrypts the values;
- writes the sanitized config;
- stores an encrypted snapshot of the exact pre-migration config and prior
  vault entries;
- appends a value-free journal record with before/after SHA-256 hashes.

If migration fails, Hi Code restores the original files and refuses to load
legacy plaintext into the desktop Runtime. This prevents a partial migration
from becoming a silent credential loss or a plaintext production path.

`electron/services/secret-store-service.mjs` exposes a controlled
`rollbackMigration(migrationId)` recovery operation. It restores the exact
pre-migration config bytes and prior vault entries and marks both encrypted
snapshot and journal record as rolled back. This recovery primitive is not
exposed as a casual renderer button because rollback can intentionally restore
legacy plaintext; it is covered by atomic rollback tests for controlled support
and migration recovery.

Legacy Agent Provider state is migrated before the Provider registry is
applied. Failure restores the previous provider state and vault transaction.

## CLI Credentials

The CLI has no Electron `safeStorage` dependency. Supply credentials through
the process environment:

```bash
export HICODE_API_KEY='...'
export HICODE_PROFILE_OPENAI_API_KEY='...'
export HICODE_PROFILE_CODER_ONE_API_KEY='...'
export HICODE_MCP_BRAVE_SEARCH_BRAVE_API_KEY='...'
hicode
```

`HICODE_API_KEY` overrides the default profile. Profile-specific names are
derived deterministically as `HICODE_PROFILE_<NORMALIZED_PROFILE>_API_KEY`.
MCP fallback names use
`HICODE_MCP_<NORMALIZED_SERVER>_<NORMALIZED_ENV_NAME>`.

The CLI can read a legacy plaintext config during the compatibility window, but
the `/model` persistence path refuses to rewrite a file containing plaintext
credentials. Migrate it with the desktop app or remove the value and use an
environment variable.

## Security Boundary

- Decryption occurs only in the Electron main process immediately before a
  model, MCP, or validated Provider path needs the value.
- Runtime/provider descriptors, events, errors, jobs, evidence, renderer state,
  and config responses exclude credential values.
- Child processes still receive the separate minimal environment policy. A
  stored model key is not automatically forwarded to Bash, Git, MCP, terminal,
  or industrial adapters.
- OS secure storage protects data at rest. It does not claim to protect a value
  from a fully compromised process running as the same logged-in user.

## Verification

```bash
npm run test:secrets
npm run test:secret-store
npm run test:providers
npm run test:services
npm run test:renderer
npm run test:security
npm run test:electron-e2e
npm run verify
```

The real Electron E2E saves a credential with the host backend, verifies that
config, vault, and journal files contain no plaintext, then tests the model by
reference. When secure storage is unavailable, the same test requires a
fail-closed save and verifies that no plaintext config was created.
